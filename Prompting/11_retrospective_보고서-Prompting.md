# 11 Retrospective 보고서

## 1. 회고 개요

이번 SHealth_A02 프로젝트는 레거시 BMI 계산 코드를 대상으로 요구사항 분석, 코드 스멜 탐지, TDD 테스트 작성, 리팩토링, 테스트 케이스 보강, Golden Master 회귀 테스트, 기능 개선, 최종 QA 검토까지 진행한 실습이다.

핵심 목표는 단순히 테스트를 통과시키는 것이 아니라, 다음 세 가지를 함께 달성하는 것이었다.

- BMI 계산과 통계 로직을 이해하기 쉬운 구조로 분리한다.
- 테스트를 통해 기존 동작과 새 기능을 안정적으로 검증한다.
- 기능 확장 이후에도 회귀 위험을 낮출 수 있는 기반을 만든다.

최종 기준으로 `mvn test`는 `SHealthBMITest` 41건과 `TexttestFixtureGoldenMasterTest` 1건, 총 42건이 모두 통과하는 상태로 확인되었다.

## 3. Refactoring 회고

### Before

초기 구조에서 가장 큰 문제는 `SHealth`가 너무 많은 책임을 가지고 있었다는 점이다. 하나의 클래스 안에서 CSV 파일 읽기, 파싱, 누락값 보정, BMI 계산, 카테고리 분류, 연령대별 통계 계산, 결과 조회까지 처리했다.

이 구조에서는 다음 문제가 발생했다.

- 기능 변경 시 수정 범위가 `SHealth.calculateBmi()`에 집중되었다.
- `18.5`, `23`, `25`, `100`, `200`, `300`, `400` 같은 매직 넘버의 의미를 코드만 보고 알기 어려웠다.
- 연령대와 BMI 카테고리별 조건문이 반복되어 수정 누락 가능성이 컸다.
- BMI `25.0` 같은 경계값에서 분류 오류가 발생할 수 있는 위험이 있었다.
- 파일 입출력과 계산 로직이 붙어 있어 순수 계산 테스트를 작성하기 어려웠다.

### After

리팩토링 후 책임은 다음과 같이 정리되었다.

- `SHealth`: 외부 호출을 받는 파사드와 기존 호환 API 유지
- `BmiDataReader`: CSV 파일 읽기와 `BmiRecord` 생성
- `BMICalculator`: BMI 계산, 카테고리 분류, 누락값 보정, 통계 계산
- `BmiRecord`: 사용자별 입력 데이터 표현
- `BmiCategory`: BMI 카테고리와 기존 타입 코드 관리
- `BmiStatistics`: 카테고리별 건수와 비율 결과 표현

가장 큰 개선은 파일 입출력과 도메인 계산 로직이 분리된 점이다. 이 덕분에 `List<BmiRecord>`만으로 계산 로직을 테스트할 수 있게 되었고, CSV나 콘솔 출력 없이도 핵심 로직을 빠르게 검증할 수 있었다.

### 느낀 점

이번 리팩토링에서 효과가 컸던 부분은 "큰 메서드를 작게 나누는 것"보다 "책임의 경계를 먼저 정하는 것"이었다. 단순히 메서드만 분리했다면 중복 조건과 매직 넘버는 여전히 남았을 가능성이 높다. 반면 `BmiCategory`, `BmiRecord`, `BmiStatistics`처럼 도메인 개념을 코드로 드러내자 테스트와 기능 추가가 자연스럽게 쉬워졌다.

어려웠던 점은 기존 API 호환성을 유지하면서 내부 구조를 바꾸는 부분이었다. `getBmiRatio(int ageClass, int type)`처럼 기존 타입 코드를 쓰는 API는 유지해야 했기 때문에, 새 enum 구조와 기존 숫자 코드 사이의 연결을 명확히 관리해야 했다.

## 4. TC 회고

### 테스트 작성 범위

테스트는 단계적으로 확장되었다.

- TDD 초기 단계에서는 BMI 계산, 평균 보정, 카테고리 경계값, 연령대별 통계 계산을 먼저 실패하는 테스트로 작성했다.
- 이후 20대, 30대, 40대별로 최소 5개 데이터를 구성하여 저체중, 정상, 과체중, 비만 비율을 검증했다.
- `weight=0`, `height=0` 누락값 보정이 같은 연령대의 유효 평균값을 사용하는지 확인했다.
- 음수 나이, 음수 체중, 음수 키는 `IllegalArgumentException`으로 차단되도록 검증했다.
- 임시 CSV 파일을 사용해 `SHealth.calculateBmi()`와 `getBmiRatio()`를 함께 검증하는 통합 테스트를 추가했다.
- `TexttestFixture` 출력은 Golden Master 테스트로 고정하여 출력 회귀를 자동 감지하도록 했다.

### 테스트가 개선에 미친 영향

테스트는 리팩토링의 안전망 역할을 했다. 특히 BMI 경계값, 연령대 분류, 누락값 평균 보정은 숫자 하나만 달라져도 결과가 조용히 틀어질 수 있는 영역이다. 테스트 데이터에 `18.5`, `23.0`, `25.0`, `20/29/30/39/40/49` 같은 경계값을 직접 포함한 것이 효과적이었다.

또한 Golden Master 테스트는 콘솔 출력처럼 단위 테스트만으로는 놓치기 쉬운 회귀를 잡기 위한 장치가 되었다. 기존 출력 형식과 값이 의도치 않게 바뀌면 `mvn test`에서 바로 확인할 수 있다.

### 테스트 작성 팁

이번 프로젝트에서 유용했던 테스트 작성 방식은 다음과 같다.

- 숫자 정책이 있는 도메인은 대표값보다 경계값을 먼저 테스트한다.
- 누락값 보정처럼 정책이 중요한 로직은 정상 케이스와 예외 케이스를 함께 둔다.
- 반복되는 연령대/카테고리 검증은 `@ParameterizedTest`와 `@CsvSource`로 표현한다.
- 테스트명과 `@DisplayName`에 Given-When-Then 의도를 드러낸다.
- 리팩토링 전후의 기존 출력은 Golden Master로 고정해 의도하지 않은 변경을 감지한다.

## 5. Feature 회고

이번 기능 개선에서는 기존 구조를 유지한 채 다음 기능을 추가했다.

- `getBmiDistributionRatio(ageClass)`: 특정 연령대의 BMI 범주별 비율 조회
- `height=0` 평균 보정: 체중뿐 아니라 키 누락값도 같은 연령대 평균으로 보정
- `getNormalBmiUserIds()`: BMI 정상 범위 사용자 ID 목록 조회
- `getOverallBmiCategoryRatios()`: 전체 사용자 대비 BMI 범주 비율 조회
- BMI 경계값 허용 오차 적용: 부동소수점 오차로 인한 경계 분류 오류 완화

기능 추가 과정에서 리팩토링의 효과가 분명하게 드러났다. 계산 책임이 `BMICalculator`에 모여 있었기 때문에 새 기능을 추가할 위치가 명확했고, `SHealth`는 외부 API를 제공하는 얇은 파사드로 유지할 수 있었다.

다만 기능 범위가 넓어질수록 acceptance criteria를 먼저 더 구체적으로 선언했으면 좋았겠다는 아쉬움이 있다. 예를 들어 같은 연령대에 유효 체중이나 유효 키가 하나도 없는 경우, malformed CSV가 들어오는 경우, 파일 읽기 실패 시 정책은 아직 추가 정의가 필요하다.

## 6. AI 활용 회고

AI는 요구사항을 테스트 가능한 시나리오로 분해하고, 코드 스멜을 우선순위화하며, 보고서 초안을 만드는 데 큰 도움이 되었다. 특히 반복적인 테스트 데이터 작성, `@ParameterizedTest` 구성, 코드 품질 이슈를 리팩토링 방향으로 연결하는 과정에서 생산성이 높았다.

효과가 컸던 순간은 다음과 같다.

- God Class, Long Method, Magic Number, 중복 로직을 리스크 중심으로 정리할 때
- TDD Red 단계에서 필요한 도메인 타입과 API를 먼저 도출할 때
- BMI 경계값과 누락값 보정 케이스를 테스트 데이터로 확장할 때
- Golden Master 테스트 절차와 갱신 방법을 문서화할 때
- 최종 QA 관점에서 커버리지, 테스트 갭, 남은 리스크를 정리할 때

반대로 AI 산출물은 반드시 검증이 필요했다. 테스트 개수, 커버리지 수치, 파일명, 실제 실행 결과처럼 사실 기반 항목은 빌드 로그와 리포트를 통해 확인해야 했다. AI는 방향을 빠르게 잡아주지만, 최종 품질 책임은 실제 테스트와 코드 리뷰에 있어야 한다.

## 7. 잘한 점

- 리팩토링 전에 코드 스멜과 결함 가능성을 먼저 정리해 우선순위를 세웠다.
- TDD 방식으로 필요한 도메인 객체와 계산 API를 자연스럽게 도출했다.
- 파일 입출력과 계산 로직을 분리해 단위 테스트 가능성을 크게 높였다.
- 기존 `getBmiRatio(ageClass, type)` API를 유지해 호환성을 보존했다.
- 단위 테스트, API 통합 테스트, Golden Master 테스트를 함께 구성했다.
- 최종적으로 전체 42개 테스트를 Green 상태로 유지했다.

## 8. 아쉬운 점과 남은 리스크

- `SHealthBMI.main()` 콘솔 진입점은 JaCoCo 기준으로 미커버 상태다.
- 같은 연령대에 유효한 체중 또는 키가 하나도 없는 경우의 정책이 명확하지 않다.
- CSV 컬럼 부족, 비수치 값, malformed CSV에 대한 실패 정책 테스트가 부족하다.
- JaCoCo coverage threshold가 `pom.xml`에 고정되어 있지 않아 CI에서 자동 차단되지는 않는다.
- 요구사항 리스크, 코드 스멜, 테스트 갭이 여러 보고서에 나뉘어 있어 하나의 risk register로 관리하면 더 좋다.

## 9. 다음 프로젝트에 적용할 액션 아이템

1. 리팩토링 전에는 characterization test 또는 Golden Master 테스트로 현재 동작을 먼저 고정한다.
2. 숫자 정책이 있는 요구사항은 경계값 중심으로 테스트 데이터를 설계한다.
3. 파일 입출력, 콘솔 출력, 계산 로직을 초기에 분리해 테스트 단위를 작게 만든다.
4. 기능 추가 전에 acceptance criteria와 예외 정책을 먼저 문서화한다.
5. 핵심 도메인 로직에는 line/branch 80% 이상의 coverage gate를 CI에 명시한다.
6. 코드 스멜, 결함, 테스트 갭, 남은 리스크를 하나의 QA risk register로 관리한다.

## 10. 최종 소감

이번 프로젝트의 가장 큰 성과는 "동작하는 코드"를 "이해하고 검증하며 확장할 수 있는 코드"로 바꾼 것이다. 초기에는 BMI 계산 로직이 하나의 큰 클래스에 숨어 있었지만, 리팩토링과 테스트를 거치면서 도메인 개념이 코드 구조로 드러났다.

테스트는 단순한 확인 절차가 아니라 설계 도구로 작동했다. 어떤 타입이 필요한지, 어떤 책임을 분리해야 하는지, 어떤 경계값이 위험한지 테스트를 작성하면서 더 명확해졌다.

다음 단계에서는 남은 예외 정책과 CLI 진입점 테스트를 보강하고, 커버리지 기준을 CI에 고정하면 현재 구조를 더 안정적으로 운영할 수 있을 것이다.
